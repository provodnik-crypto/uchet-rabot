# Как запустить и проверить

## Разовая настройка (делается один раз, с помощью Claude)

### 1. Supabase — база данных и вход
1. Зайдите на https://supabase.com → **Start your project** → войдите через GitHub.
2. **New project**: имя `uchet-rabot`, регион **Central EU (Frankfurt)**, придумайте
   пароль базы и **сохраните его** (понадобится на шаге 3).
3. Создайте токен доступа: аватар справа сверху → **Account preferences** →
   **Access Tokens** → **Generate new token** (имя `claude`).

### 2. Expo — публикация приложения на телефон
1. Зарегистрируйтесь на https://expo.dev.
2. Аватар → **Account settings** → **Access tokens** → **Create token** (имя `claude`).
3. На телефон поставьте **Expo Go** из Google Play или App Store.

### 3. Передать доступы Claude (не через чат!)
В claude.ai/code: меню облачного окружения в заголовке сессии → **Edit**.
* **Network access** → в **Allowed domains** добавьте:
  `supabase.co`, `*.supabase.co`, `api.supabase.com`, `expo.dev`, `*.expo.dev`.
* **Environment variables** добавьте:
  ```
  SUPABASE_ACCESS_TOKEN=<токен из шага 1.3>
  SUPABASE_DB_PASSWORD=<пароль базы из шага 1.2>
  SUPABASE_PROJECT_REF=<строка из адреса проекта: supabase.com/dashboard/project/ЭТА_СТРОКА>
  EXPO_TOKEN=<токен из шага 2.2>
  ```
* Сохраните и начните **новую сессию** (переменные подхватываются при старте),
  напишите в ней «продолжаем этап 1, доступы добавлены».

Дальше Claude сам: применит миграции к базе, развернёт функцию `admin-users`,
создаст первого руководителя и опубликует приложение через EAS Update.

## Этап 2. Что проверить на телефоне
Обновление приходит в установленное приложение само: откройте его, подождите 10–20 секунд,
полностью закройте (смахните из недавних) и откройте снова. На главной руководителя
появятся плитки «Прайс» и «Отделы».
1. **Прайс** → «Найдено: 1399» (работы, которые видят мастера). Фильтры «Выключенные»,
   «Материалы», «Все» (2907).
2. Поиск: «розетк», «светильник», «монтаж светильник» — несколько слов сужают поиск.
3. Откройте позицию → видны полное название, единица, цена и история цен.
   Введите новую цену → «Сохранить цену» → в истории появилась строка «вручную»,
   старая цена осталась.
4. Фильтр «Выключенные» → откройте позицию → «Включить позицию» → она появилась в «Активных».
5. **Отделы**: 7 отделов, «Магазин» — по умолчанию. Добавьте «склад» → сохранится как «Склад»;
   повторно «СКЛАД» → ошибка (дубль). Сделайте другой отдел основным, выключите лишний.

Загрузка прайса в базу: `python3 supabase/scripts/price_2026_seed.py > /tmp/p.sql` и выполнить SQL.
Повторный запуск безопасен — ручные правки не затираются.

## Этап 3. Что проверить на телефоне (под мастером)
Обновление приходит само (открыть, подождать 10–20 с, закрыть и открыть снова).
1. Войдите как мастер → «Закрыть смену» → «Сегодня».
2. Заявка: RFS, наберите `2604232283` → видно `RFS260423_2283` → «Дальше».
   Неверный номер (меньше цифр, месяц 13) → понятная подсказка.
3. Поиск «скамеек» → выберите работу → объём `3`, добавьте напарника → «Добавить в смену».
4. «+ Работа по RFS…» → «Работы нет в прайсе» → «Распил МДФ»: появится подсказка из прайса;
   выберите свою работу, единицу «м», объём `2,5` → «Добавить в смену».
5. «+ Другая заявка» → «Без заявки» → любая работа.
6. «Проверить и отправить» → нигде нет рублей → «Отправить» → «Смена отправлена».
7. Выключите интернет и отправьте ещё одну смену → «Не отправлено… Повторить»;
   закройте приложение — черновик сохранился («Продолжить смену»); включите интернет → «Повторить».
8. «Моя история»: статусы «Принято» / «На оценке», кнопка «Изменить смену» (только сегодня).
9. Войдите как напарник → он видит в истории работы, где он исполнитель.

## Этап 4. Что проверить
Под мастером внесите смену с 2–3 работами «вне прайса», затем войдите руководителем.
1. Главная: сумма за месяц, счётчик «На оценке», строка «Без цены… в сумму не входят».
2. **На оценке** → работа → «Назначить цену» (видна итоговая сумма), галочка «Добавить в прайс».
   Позиция появилась в «Прайс» с категорией «Добавлено вручную»; мастер теперь находит её поиском.
3. Вторая работа → «Заменить на прайс» → найдите позицию → «Заменить» (цена из прайса).
4. Третья → «Отклонить» с комментарием. Под мастером: на главной «Отклонено работ: 1» →
   история → «Исправить и отправить снова» → работа снова «На оценке».
5. Внесите ту же работу вне прайса ещё раз → в очереди подсказка «Раньше оценивали: …».
6. **Сводка**: итог, по сотрудникам (сумма долей = итог), по месяцам; периоды.
7. **Работы**: фильтры по периоду, сотруднику, отделу, статусу, заявке; откройте работу →
   измените объём/исполнителей → сумма пересчитана по прежней цене; удаление.
8. **Заявки**: поиск, заполните тему (без имён и телефонов).

## Доработка «Заявки из ITSM» (13.10.2026)
Нужна новая версия приложения (APK, версия среды 3): в ней модуль выбора файла.
* Руководитель раз в день загружает выгрузку ITSM (.xlsx). Файл читается и очищается **на телефоне**:
  телефоны и почты → «[тел. удалён]», ФИО заявителя из описания удаляется, заявитель — «Имя Ф. (ldap)»,
  лишние столбцы отбрасываются. В базу — только очищенные строки; файл нигде не сохраняется.
* Предпросмотр: подсчёты, период по дате регистрации (производственный календарь РФ 2026–2027),
  «вне выбранного периода» с «Загрузить тоже», «Пропали из файла» (Закрыть/Оставить), подсветка
  слов, похожих на имена, с правкой, пример 3 строк. Журнал загрузок — `request_imports`.
* Мастер выбирает заявку из списка магазина (назначенные ему — сверху), ручной ввод — «Нет в списке».
  Заявки, отмеченные мастером «Выполнено», в списке не показываются.
* Проверки: `supabase/tests/11_itsm_requests.sql`, `cd app && npm run test:itsm`. На файле 13.10.2026
  (252 строки) проверено на копии базы: первая загрузка — 252 заявки магазина 031, повторная — 0;
  заявители «Имя Ф. (номер)», телефонов в описаниях нет.

**Закрыть старые заявки (13.10.2026, миграция `20261013000002_close_old_requests.sql`):** «Заявки» →
«Закрыть старые заявки», по умолчанию старше 30 дней; вкладки «Открытые / Закрытые / Все».
Проверки: `supabase/tests/12_close_old_requests.sql`. Откат: обновление с коммита `636875e`
и `supabase/rollback/20261013000002_close_old_requests_down.sql`.

**Заявки отдельно от смены (14.10.2026, миграция `20261014000001_request_card.sql`):**
* Главная мастера → «Заявки» (Назначено вам / Новые; «Новые» — после последнего просмотра, отметка на телефоне)
  → список (`(master)/req`) → карточка заявки (`(master)/req/[id]`): полный текст, назначение, работы всех мастеров
  без денег, «Внести работы по заявке» (смена сегодняшней датой → сразу выбор работы).
* При закрытии смены у заявки значок «i» → та же карточка с «Выбрать эту заявку». На «Выборе работы» — суть заявки.
* Прайс: 63 названия-обрывка исправлены, старые названия — в `price_item_renames`.
* Проверки: `supabase/tests/13_request_card.sql`. Откат: обновление с коммита `64fbd10`
  и `supabase/rollback/20261014000001_request_card_down.sql` (вернёт и старые названия прайса).

**Жизненный цикл заявки, часть 1 (14.10.2026, миграция `20261014000002_request_lifecycle.sql`):**
* Статусы: Ожидает → В работе (мастер взял, примерное время = план, напарники) → На проверке → Принята;
  Возвращена = снова «В работе» с комментарием; У подрядчика. История — `request_events`.
* Взять может только один: `take_request` — одна операция `update … where status = 'waiting'`.
  Работы по чужой заявке не принимает и `submit_shift` (обёртка над прежней, теперь `submit_shift_core`).
* Деньги: работа по заявке получает цену, но статус `awaiting` («Ждёт приёмки»); `accept_request` переводит в `priced`.
  Работы без заявки и все работы до доработки (`needs_acceptance = false`) — как раньше. Деньги делятся поровну между исполнителями.
* «Не закончено» убрано; `requests.state` держится в согласии со статусом (для статистики «Время» и Excel).
* Мастер: «Мои заявки» на главной, карточка (взять, + работа, время за сегодня, проверить и отправить, отказаться),
  «Закрыть смену» — итог дня. Руководитель: «На проверке» (принять / вернуть), фильтры в «Заявках», приоритет, снять/переназначить.
* Перенос данных: «выполнена» → «Принята»; ручные номера до доработки → «Принята»; остальные открытые → «Ожидает».
* Проверки: `supabase/tests/14_request_lifecycle.sql`. Откат: обновление с коммита `53d90c1` и
  `supabase/rollback/20261014000002_request_lifecycle_down.sql`.

**Жизненный цикл заявки, часть 2 (15.10.2026, миграция `20261014000003_request_comments.sql`):**
* Переписка в карточке заявки (мастер и руководитель): `add_request_comment`, события и сообщения — одна лента `request_events`.
* Непрочитанное: `request_reads` (когда открыл карточку) и `request_unread`; метка «💬 N нов.» в списках.
* Уведомления только внутри приложения (`my_notifications`): мастеру — вернули, новое сообщение, срочные;
  руководителю — новые сообщения, отказы, отправки, «без действий больше 3 рабочих дней» (`working_days_since`).
  Пуш-уведомлений нет — отдельный этап (нужен проект Firebase и новый APK).
* Проверки: `supabase/tests/15_request_comments.sql`. Откат: обновление с коммита `220978d`
  и `supabase/rollback/20261014000003_request_comments_down.sql`.

**Ручные заявки с простыми номерами (16.10.2026, миграция `20261016000001_manual_requests.sql`):**
* «+ Новая заявка» у мастера (список заявок; «Нет в списке» при закрытии смены) и у руководителя («Заявки»).
  Номер — `manual_request_seq`, общий для всех: 1, 2, 3… Показывается как «№ 12» (`requestLabel`).

## Доработка «Время по заявкам» (12.10.2026)
* Мастер по каждой заявке смены отмечает время (30 мин / 1 ч / 2 ч / 4 ч / вся смена или ±15 мин)
  и статус «Выполнено» / «Не закончено». Больше 8 ч за смену — предупреждение (отправить можно).
* Незаконченная заявка у автора переходит в начало следующей смены с пометкой «Перенесено с ДД.ММ»;
  время и работы копятся. Руководитель может закрыть заявку сам или вернуть в работу.
* Руководитель: план в «Заявках» (красная рамка — факт больше плана), раздел «Время»
  (среднее и медиана по видам работ, мастера против среднего по тем же видам, дольше плана, доля переносов),
  лист «Время» в Excel.
* Правила расчёта: вид работ — категория прайса (у работ вне прайса — «Работы вне прайса»); время заявки
  делится между работами по стоимости (до оценки — поровну); совместная работа засчитывается каждому
  исполнителю целиком; в среднее входят только выполненные заявки; работы без заявки за смену — одно задание.
* Проверки: `supabase/tests/10_request_time.sql` (27 проверок).

**Откат, если понадобится:**
1. Код: вернуть приложение к коммиту `a66d9a0` (последняя версия до доработки) и выпустить обновление
   `eas update` с этого коммита. Новый APK не нужен.
2. База: выполнить `supabase/rollback/20261012000001_request_time_down.sql` (удаляет время, планы и статусы заявок).
3. Данные базы на 12.10.2026 до доработки: хранилище Supabase → папка `backups` → `db_backup_2026-10-12.json.gz`.
